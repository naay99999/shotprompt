# ShotPrompt: คะแนนหลายหมวดและการคัดช่วงเด่น

วันที่: 2026-10-02
สถานะ: รอผู้ใช้ตรวจสเปก ก่อนจัดทำแผน implementation

## เป้าหมายและขอบเขตการอนุมัติ

ผู้ใช้อนุมัติทิศทางข้อเสนอในแชต: เพิ่มประเภทเนื้อหา คะแนนหลายด้านพร้อมเหตุผล การเลือกช่วงให้จบความ ลดคลิปซ้ำ ค้นหาตามความต้องการ Feedback และประเมินใหม่จากข้อมูลเดิม เป้าหมายคือช่วยคัดคลิปได้หลายแนวและลดเวลาที่ต้องแก้ช่วงแนะนำด้วยมือ

สมมติฐานของสเปก: ทำงานในเครื่องเป็นค่าเริ่มต้นตามโครงการ รองรับชุดเกณฑ์ภาษาไทยและอังกฤษก่อน และใช้โครงสร้าง Bun/core/db/Elysia/Next.js เดิม คะแนนใช้จัดลำดับความเหมาะสมตามเกณฑ์ ไม่ใช่ความน่าจะเป็นที่จะไวรัล

งานนี้มีสามโครงการย่อยเรียงลำดับ สเปกฉบับนี้กำหนดรายละเอียดสำหรับโครงการ A ส่วน B และ C เป็นขอบเขตต่อยอดที่ต้องออกแบบแยก ไม่ถือว่าส่งมอบแล้วเมื่อ A เสร็จ

## ลำดับโครงการ

### A — ระบบหลายหมวดในเครื่องและวงจรประเมินใหม่

- หมวด sales, podcast, education, story เลือกหนึ่งหรือหลายหมวดได้
- เป้าหมาย balanced, sell, teach, entertain, drive-full-video พร้อมช่วงความยาว
- คะแนน 0–100 แยกด้าน เหตุผลที่อ้างอิงบทถอดเสียง และระดับหลักฐาน
- สร้างช่วงจากกลุ่มบทพูด เลือกขอบเขตด้วยสัญญาณการจบประเด็นและช่องว่างเวลา
- ลดช่วงซ้อนและเนื้อหาซ้ำ พร้อมเปิดดูรายการที่ถูกซ่อนได้
- ข้อความระบุหัวข้อที่ต้องการ ใช้การจับคำ/วลีในระยะนี้
- Feedback และการประเมินใหม่โดยใช้ transcript/scenes เดิม
- เก็บประวัติการวิเคราะห์ ป้องกันผลใหม่เขียนทับผลที่ใช้งานอยู่เมื่อเกิดข้อผิดพลาด

### B — วิเคราะห์ความหมายด้วยโมเดลภาษา

- ประเมินความครบของคำตอบ ความน่าสนใจ และเรื่องเล่าจากบริบท
- คำสั่งภาษาธรรมชาติ เช่น “ข้อผิดพลาดมือใหม่” ที่ไม่ต้องตรงคำในบทพูด
- แนะนำหมวดโดยอัตโนมัติ พร้อมให้ผู้ใช้แก้
- ตัวเชื่อมโมเดลในเครื่องก่อน และบริการภายนอกแบบผู้ใช้เลือกเปิดใช้
- ก่อน implementation ของ B ต้องเลือก runtime/model จากเครื่องจริง กำหนดขนาดข้อมูล เวลาและหน่วยความจำที่ยอมรับได้ รวมถึงนโยบายข้อมูลของบริการภายนอก
- โมเดลเสนอได้เฉพาะขอบเขตที่อ้างอิง segment จริง ผลลัพธ์ต้องผ่าน schema/range validation; timeout, output ผิดรูปแบบ และ model unavailable ต้องแสดงสถานะชัดเจน

### C — ภาพและเสียง รวมทั้งหมวดเฉพาะทาง

- ตลก ข่าว เกม กีฬา Vlog ท่องเที่ยว และอาหาร
- สัญญาณจากการสาธิต เหตุการณ์ในภาพ ปฏิกิริยาและเสียง โดยประเมินความเหมาะสมแยกแต่ละหมวด
- การตรวจเสียงเงียบ คุณภาพเสียง และขอบเขตฉากที่ละเอียดขึ้น
- ปรับเกณฑ์จากข้อมูล Feedback หลังมีชุดตัวอย่างเพียงพอ ไม่อ้างว่าระบบเรียนรู้เพียงเพราะเก็บ Feedback

## หลักฐานจากโค้ดปัจจุบัน

- `packages/core/src/hooks.ts`: คะแนนจาก substring keywords, threshold 40 และ scene-only score 35; รวมช่วงด้วยคะแนนสูงสุด และขยายขอบเขตหลังจำกัดความยาว
- `packages/core/src/keywords.ts`: ชุดคำเริ่มต้นไทย/อังกฤษเน้นการขาย
- `apps/server/src/steps/detect-hooks.ts`: ลบ candidates ก่อนบันทึกชุดใหม่
- `packages/db/src/schema.ts`: candidates เก็บคะแนนเดียว; clips อ้าง candidate แบบ soft reference
- `apps/server/src/pipeline.ts`: pipeline ลบ audio.wav เมื่อสำเร็จ จึงยังไม่ควรแสดงคะแนนคุณภาพเสียงจากการประเมิน transcript อย่างเดียว
- `apps/server/src/queue.ts`: คิวเดิมรองรับ pipeline/export และมี cancel ผ่าน AbortSignal
- `apps/web/components/candidate-panel.tsx`: แสดงเวลา คะแนนเดียว และปุ่มเพิ่มเป็นคลิป
- workspace มีการแก้ไขเดิมจำนวนมาก ต้องต่อยอดจากเนื้อหาปัจจุบันและไม่ย้อนงานเหล่านั้น

## แนวทางที่เลือกและทางเลือก

แนวทางที่เลือกคือทำระบบคะแนนแบบกฎที่อธิบายได้ พร้อมข้อมูลเวอร์ชันและรอบการวิเคราะห์ แล้วเพิ่มตัวประเมินเชิงความหมายใน B วิธีนี้ส่งมอบฟีเจอร์ใช้งานได้โดยไม่บังคับติดตั้งโมเดลเพิ่ม และสร้างฐานสำหรับเปรียบเทียบคุณภาพกับโมเดลภายหลัง

ทางเลือกเพิ่มรายการคำอย่างเดียวแก้ได้เร็ว แต่ยังมีปัญหาคะแนนสะสมจากช่วงยาวและไม่มีประวัติผล ทางเลือกเริ่มจากภาพ/เสียง/โมเดลทั้งหมดพร้อมกันทำให้ประเมินสาเหตุของผลผิดและข้อจำกัดเครื่องได้ยาก จึงแยกเป็นโครงการต่อเนื่อง

## การใช้งานโครงการ A

1. หน้าอัปโหลดมีส่วน “การคัดช่วงเด่น” เลือกหมวดได้หลายหมวด ค่าเริ่มต้นทั้งสี่หมวด เป้าหมาย balanced และความยาว 15–60 วินาที
2. ผู้ใช้ตั้ง min/max ได้ระหว่าง 5–180 วินาที โดย min <= max; วิดีโอที่สั้นกว่า min ใช้ช่วงเต็มที่มีและแจ้งว่าเนื้อหาสั้นกว่าที่ขอ
3. ช่อง “หัวข้อที่ต้องการ” ยาวสูงสุด 500 ตัวอักษร ช่วยเพิ่มอันดับช่วงที่ตรงคำในระยะ A พร้อมข้อความอธิบายข้อจำกัด ไม่เรียกว่าเข้าใจคำสั่งอิสระ
4. หน้า workspace แก้ค่าข้างต้นแล้วกด “ประเมินช่วงใหม่” แสดงสถานะงานและให้ยกเลิกได้ ผลรอบก่อนยังเปิดดูและเลือกเป็นคลิปได้
5. การ์ดแสดงคะแนนรวม /100, หมวดหลักและหมวดรอง, แหล่งการประเมิน, เหตุผลไม่เกินสามข้อ, คำเตือนจุดตัด และรายละเอียดคะแนนที่เปิดดูได้
6. ตัวกรองหมวด คะแนนขั้นต่ำ และรายการซ้ำทำงานกับผลรอบปัจจุบัน ไม่ต้องประมวลผลใหม่
7. Feedback เลือก good, irrelevant, starts-mid-thought, ends-too-soon, duplicate พร้อมล้างหรือเปลี่ยนได้
8. คะแนนเดิมที่ยังไม่มีเวอร์ชันแสดงว่า “คะแนนระบบเดิม” ไม่เติม /100 และไม่เปรียบเทียบกับผลใหม่โดยตรง

## การสร้างช่วงและขอบเขต

core รับ segments ที่เรียงตามเวลา, scenes, duration และ options โดยไม่อ่านไฟล์หรือฐานข้อมูล

- สร้างจุดเริ่มจากต้นกลุ่มบทพูดหลังช่องว่างอย่างน้อย 1.5 วินาที จุดเปลี่ยนฉาก และจุดเริ่ม segment ที่พบสัญญาณตามหมวด
- สร้างช่วงต่อเนื่องหลายความยาวภายใน min/max จากเวลา segment จริง; หยุดเมื่อพบจุดจบเหมาะสมใกล้ความยาวเป้าหมาย
- ใช้ punctuation ช่องว่างเวลา และคำบอกการสรุปเป็นสัญญาณขอบเขต ไม่รับประกันว่าหนึ่ง segment คือหนึ่งประโยค โดยเฉพาะภาษาไทย
- ถ้าจุดเริ่มดูเหมือนต่อจากประโยคก่อน ให้ลองรวม segment ก่อนหน้า และถ้าจุดจบยังไม่ครบให้ลองขยาย ทั้งสองอย่างต้องไม่เกิน max และ duration
- padding ต้องอยู่ภายในความยาวสูงสุดสุดท้าย ไม่เพิ่มหลังตรวจ max แล้ว
- ถ้าขยายแล้วเกินข้อจำกัด ให้คงช่วงที่ถูกต้องพร้อมคำเตือนว่าอาจเริ่มหรือจบกลางประเด็น
- ช่วงจากฉากอย่างเดียวจัดเป็น “ช่วงจากภาพเปลี่ยน” หลักฐานจำกัด ไม่ให้คะแนนเนื้อหาเพราะตรวจพบฉากตัด
- ถ้าไม่มีทั้ง transcript และ scenes ให้ผลว่างและเสนอการเลือกช่วงเอง
- จำกัดผลก่อนคัดซ้ำที่ 500 ช่วง และผลหลักที่ 30 ช่วง เพื่อควบคุมงานบนวิดีโอยาว การเลือกต้องกระจายตลอดวิดีโอ ไม่ตัดทิ้งทุกอย่างหลัง 500 ช่วงแรก

## เกณฑ์และคะแนน

คะแนนแต่ละด้านอยู่ในช่วง 0–100 จากสัญญาณที่ตรวจได้จริง:

| ด้าน | หลักฐานในโครงการ A |
| --- | --- |
| hook | คำถาม การเปิดปัญหา คำเตือน หรือประโยคเปิดตามหมวด |
| categoryFit | กลุ่มสัญญาณตามหมวด เช่น ปัญหา+วิธีแก้, คำถาม+คำตอบ, ประโยชน์+ข้อเสนอ |
| completeness | สัญญาณต้น/ท้าย ช่วงต่อเนื่อง และคำบอกคำตอบหรือสรุป |
| pacing | สัดส่วนช่วงมีบทพูดและช่องว่างจาก timestamps; ไม่แปลเป็นอารมณ์หรือน้ำเสียง |
| goalFit | สัญญาณตรงเป้าหมาย และคำ/วลีตรงหัวข้อเมื่อผู้ใช้ระบุ |

ไม่แสดงคะแนนคุณภาพภาพ เสียง ความตลก หรือความถูกต้องของข้อเท็จจริงโดยไม่มีตัววิเคราะห์รองรับ

น้ำหนักเริ่มต้นตามลำดับ hook/categoryFit/completeness/pacing/goalFit:

| หมวด | น้ำหนัก (%) |
| --- | --- |
| sales | 20 / 25 / 20 / 10 / 25 |
| podcast | 20 / 20 / 35 / 10 / 15 |
| education | 15 / 25 / 35 / 10 / 15 |
| story | 25 / 20 / 30 / 15 / 10 |

คำนวณทุกหมวดที่เลือก หมวดหลักคือหมวดที่ได้คะแนนสูงสุด เก็บคะแนนและหลักฐานของทุกหมวดไว้ การเลือกหลายหมวดไม่บวกคะแนนหมวดเข้าด้วยกัน ส่วน goalFit ใช้เกณฑ์เป้าหมายที่เลือก; balanced ใช้ความเหมาะสมตามหมวด

การจับคำต้องจัดการคำซ้อน: เช่น “ส่งฟรี” และ “ฟรี” ในตำแหน่งเดียวกันใช้หลักฐานเดียว ใช้ word boundaries ภาษาอังกฤษ และวลี/การตัดคำภาษาไทยตามความสามารถของ runtime พร้อม fallback ที่ทดสอบได้ กำหนดเพดานแต่ละกลุ่มสัญญาณ; การพูดคำเดิมซ้ำและคลิปยาวขึ้นไม่เพิ่มคะแนนโดยไม่จำกัด

เหตุผลต้องสร้างจากรหัสสัญญาณและอ้าง segment ID/time/ข้อความที่พบจริง ไม่เขียนคำอธิบายว่าคลิปดีในมิติที่ยังไม่ได้ตรวจ

ระดับหลักฐานใช้ limited/moderate/strong ตามการมีบทพูด ภาษาที่รองรับ และจำนวนกลุ่มสัญญาณที่อิสระต่อกัน แสดงว่าเป็นความครบของหลักฐานตามกฎ ไม่ใช่ความมั่นใจทางสถิติหรือความแม่นยำของ Whisper ซึ่งยังไม่ได้เก็บ

สำหรับภาษาอื่นยังสร้างช่วงจาก timestamps/scenes ได้ แต่แสดง “ชุดเกณฑ์ภาษานี้ยังไม่รองรับ” เก็บด้านที่ประเมินไม่ได้เป็น null และคะแนนรวมเป็น null ไม่ตีความการไม่มีคำสำคัญว่าเนื้อหาไม่ดี กรณีนี้แสดงการเรียงตามเวลาและปิดตัวกรองคะแนน

## การลดคลิปซ้ำ

- ช่วงที่ overlap / shorter duration >= 0.7 ถือเป็นกลุ่มซ้อน
- เนื้อหาซ้ำใช้ normalized token/character shingles และ Jaccard >= 0.8; ข้อความว่างห้ามจัดว่าซ้ำเพียงเพราะว่างเหมือนกัน
- เลือกคะแนนสูงสุดเป็นตัวแทน; เสมอกันเลือกคำเตือนน้อยกว่า แล้วเวลาเริ่มก่อน
- เก็บ suppressedBy และเหตุผลไว้ให้เปิดดูได้ ไม่ลบรายการเงียบ ๆ
- ระยะ A ลดความซ้ำเชิงข้อความ ยังไม่อ้างว่าเข้าใจหัวข้อเดียวกันที่ใช้คำต่างกัน ซึ่งอยู่ใน B

## ข้อมูลและความเข้ากันได้

เพิ่ม `analysis_runs`: id, videoId, jobId, status, optionsJson, engineVersion, sourceRevision, createdAt, completedAt, error และเพิ่ม `videos.activeAnalysisRunId` แบบ nullable

sourceRevision เป็น hash ของ segments/scenes/duration/language ที่นำมาคำนวณ ทุก run เก็บ options แบบ immutable โดย jobs ใช้ type analysis สำหรับการประเมินใหม่

เพิ่ม candidates.runId และ assessmentJson แบบ nullable assessment มี schemaVersion, engine, categoryScores, dimensions, reasons, warnings, evidenceLevel และ suppressedBy เปลี่ยน score ให้ nullable สำหรับข้อมูลที่ยังประเมินไม่ได้ ต้อง migration SQLite แบบ transactional และรักษาข้อมูลเดิมทุกแถว

เพิ่ม `candidate_feedback`: candidateId (unique), videoId, runId, verdict, updatedAt; ให้ระบบ single-user เก็บ verdict ล่าสุดต่อ candidate พร้อมคัดลอก feedback ไปเป็น snapshot ใน clip assessment เมื่อต้องการหลักฐานการเลือก

เพิ่ม clips.assessmentJson เพื่อเก็บคะแนน/options/source ของ candidate ตอนเลือก คลิปเดิม score แบบ legacy ยังคงเดิม คลิปที่แก้ช่วงภายหลังแสดงว่าคะแนนเป็นของช่วงแนะนำเดิม และเก็บ evaluatedStart/evaluatedEnd เพื่อตรวจความแตกต่าง

ไม่ลบ candidates/runs เก่าเมื่อประเมินใหม่ จึงไม่ทำลาย candidateId ของคลิปและ Feedback การลบวิดีโอต้องลบข้อมูลใหม่ทั้งหมดตามลำดับที่ถูกต้อง รวมถึงไฟล์ thumbnail ที่เกี่ยวข้อง

## Server และวงจรงาน

- เพิ่ม analysis service/runner ที่อ่าน snapshots, เรียก core, สร้าง thumbnails เฉพาะรอบใหม่ แล้วบันทึกผลและเปลี่ยน activeAnalysisRunId ใน transaction เดียว
- initial pipeline ใช้ service เดียวกันจาก detect-hooks/thumbnails; publish ผลเมื่อขั้นตอนที่จำเป็นสำเร็จ ห้ามมีสองเส้นทางคำนวณคะแนนที่ไม่ตรงกัน
- งาน analysis ไม่ถอดเสียง ไม่ normalize ไม่ extract audio ใหม่ และไม่เปลี่ยนสถานะ video จาก ready เป็น processing
- บล็อกการเริ่ม pipeline/analysis ซ้อนกันสำหรับ video เดียวด้วยการตรวจใน transaction; กลับ 409 พร้อม jobId ที่กำลังทำงาน
- ก่อน publish ตรวจ sourceRevision อีกครั้ง; ถ้าข้อมูลเปลี่ยนให้ run ล้มเหลวด้วยข้อความขอประเมินใหม่ ผลเดิมยัง active
- cancel หรือ failure ต้องเก็บผลเดิม ยกเลิก child process และล้าง temporary thumbnails ของรอบที่ล้มเหลว
- restart เปลี่ยน queued/running analysis ที่ค้างเป็น failed พร้อมเหตุผล interrupted ให้ผู้ใช้กดลองใหม่ได้ โดยไม่ publish partial results
- emit analysis:update/job:update พร้อม videoId/runId; frontend refetch เมื่อสำเร็จหรือ reconnect
- options จำกัด enum, categories 1–4 ค่าไม่ซ้ำ, ตัวเลข finite และช่วงเวลา, query <=500 ก่อนสร้างงาน

API เพิ่มเติม:

- `GET /analysis/profiles`: หมวด เป้าหมาย defaults และความสามารถที่รองรับ
- `POST /videos/:id/analysis`: options -> 202 { runId, jobId }
- `GET /videos/:id/analysis`: active run, latest run และรายการประวัติสูงสุด 20 รอบล่าสุด
- `PUT /videos/:id/candidates/:candidateId/feedback`: verdict; ตรวจ candidate อยู่ใน video จริง
- `DELETE /videos/:id/candidates/:candidateId/feedback`: ล้าง verdict
- `GET /videos/:id/candidates`: รักษารูปแบบ array เดิม เพิ่ม optional runId/includeSuppressed; default active run และซ่อน suppressed; กรณีไม่มี active run คืน legacy candidates
- ใช้ cancel job endpoint เดิมโดยเพิ่ม dispatch ไป analysis queue

404 สำหรับ video/run/candidate ที่ไม่มีหรือไม่สัมพันธ์กัน, 400 สำหรับ options ผิดรูปแบบ, 409 สำหรับงานชนหรือข้อมูลต้นทางยังไม่พร้อม

## การแบ่งความรับผิดชอบ

- core: profiles, candidate windows, signal extraction, scoring, deduplication และ shared contracts เป็น pure functions แยกไฟล์ตามหน้าที่
- db: schema/migration และ run/feedback persistence
- server: queues, snapshots, transactions, API validation, cancellation, thumbnail lifecycle
- web: analysis controls, score details, filters, feedback และสถานะงาน ใช้ UI pattern เดิม; อ่าน installed Next.js docs ก่อน implementation
- ไม่เพิ่ม dependency สำหรับโมเดลภาษาใน A; จุดต่อของ evaluator ใช้ input/output contract เดียวกันเพื่อเพิ่ม B ภายหลัง

## การตรวจรับ

- fixture ไทย/อังกฤษของทั้งสี่หมวดได้ช่วงที่คาดหวังและมีเหตุผลจากข้อความจริง; ปฏิเสธเหตุผลที่ไม่มีหลักฐาน
- คำซ้อนและคำซ้ำไม่ทำให้คะแนนพุ่ง; คะแนน finite อยู่ในช่วง 0–100 และรวมตามน้ำหนักได้ตรง
- ช่วงไม่เกิน duration/max หลัง padding; ครอบคลุมวิดีโอสั้น ข้อความว่าง และภาษาไทยไม่มี punctuation
- scene-only และภาษาที่ไม่รองรับแสดงข้อจำกัด/null ได้ครบทั้ง API/UI ไม่กลายเป็น 0 คะแนนโดยปริยาย
- ลดช่วงซ้ำได้ เปิดดูผลที่ซ่อนได้ และไม่จับข้อความว่างว่าซ้ำ
- migration เปิด DB เก่าและเปิดซ้ำได้โดยไม่เสีย clips/subtitles/exports
- ประเมินใหม่ไม่เรียก Whisper; failure/cancel/restart/race ไม่ทำลาย active results หรือคลิปที่เลือกไว้
- API ป้องกัน cross-video IDs และ options ที่ไม่ถูกต้อง
- Feedback เปลี่ยนและล้างได้; คลิปที่แก้ช่วงไม่แสดงคะแนนเดิมเสมือนประเมินใหม่แล้ว
- ตรวจ responsive UI, keyboard access และหน้าจอคะแนน legacy/empty/loading/error
- หลัง implementation รัน focused tests, bun test, bun run typecheck และ web production build; บันทึกปัญหาที่มีอยู่เดิมแยกจากปัญหาที่เกิดจากงานนี้

ตรวจคุณภาพกับคลิปจริงที่ผู้ใช้มีสิทธิ์ใช้ก่อนอ้างว่าคัดคลิปดีขึ้น: บันทึกอัตราการเลือก candidate, ระยะเวลาแก้ start/end และเวลาคัดคลิป ข้อมูล Feedback อย่างเดียวไม่พิสูจน์คุณภาพโมเดล ชุดทดสอบอัตโนมัติพิสูจน์พฤติกรรมตามกฎเท่านั้น
